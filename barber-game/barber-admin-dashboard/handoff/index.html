Barber Admin Dashboard
Chop It Up Barbershops

A mobile-first redesign of the legacy administration panel, refined with real-time feedback from owner Mervis. This document separates implemented UX from simulated data and outlines the work to connect it to Barbergame.

Working in the demo

  • One scrolling page; four-item fixed mobile navigation; slide-up editors.
  • Eight sample bookings, clickable KPI, future appointments through year-end, client-contact details and required-reason cancellation.
  • Past appointment history, status filters and detail views.
  • Searchable clients, contact preview and an on-demand Blocked Clients sheet with View Details and Unblock; no permanent blocked-client card on the page.
  • Weekly hours and new appointments with 15-minute arrow controls; individual tappable 30-minute availability blocks with color states; preset services dropdown with custom descriptions and larger arrow steppers.
  • Barber profile editor with identity/contact details, social links, bio and experience, plus separate browser-local portrait editing; responsive UI. Shop Information has been removed entirely from the barber dashboard; it belongs to owner/admin workflows.
  • Barber Messages at the bottom: Received/Sent history and simulated compose to all barbers, shops, or individual barbers. Required read-and-confirm screen appears after fresh demo login when announcements are pending, and on dashboard entry (after v0.3 checkpoint).

Not connected to production

  • No live booking, customer, shop, service or availability API/database.
  • No live appointment creation, cancellation, availability block enforcement or server persistence.
  • Barber photo, blocked-client flags, inbox and time blocks are browser-local; other edits reset on refresh.
  • Earnings and dashboard totals are illustrative, not ledger-derived. The 7-day free booth-rent voucher is a non-redeemable demo concept. The printable income statement is conspicuously SAMPLE / not valid proof of income.
  • No production authentication/authorization, notifications, audit logging or payment processing.
  • No messaging API, real recipient directory or delivery; the required acknowledgment gate is browser-local, not server-enforced post-login, and produces no real per-user read receipt.

Recommended development sequence

01 / Contracts + security

Confirm existing Barbergame APIs, canonical records and roles; establish production authentication and permissions.

02 / Operational workflows

Connect appointments, client lookup, services, availability and time off. Derive KPIs from the same data.

03 / Persistence + QA

Add secure photos, financial summaries, edge cases, error states and real-device/accessibility tests.
