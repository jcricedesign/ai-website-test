Migration history · November 10–11, 2026

How we got here.

The goal was to establish one owner-controlled BarberGame shop directory. We started with an authoritative Designworks SQLite file, moved its complete contents into TBG Networks LLC’s Cloudflare account, and changed the existing customer Worker to read that database. This page records the decisions and locations so the setup can be recovered later.

  1. Selected the authoritative corpus.
    351 Designworks-owned shop records, not the larger unrelated directory returned by the old API. No merges and no pre-migration cleanup.
  2. Imported and verified all 351 rows.
    Private SQL export on Designworks → barbergame-directory D1. Verification: 7 confirmed, 344 entered; 88 distinct raw city values. Nine missing/invalid coordinates retained for later enrichment.
  3. Rewired the customer website.
    The existing barbergame-customer Cloudflare Worker now reads via DIRECTORY_DB. Search, city browsing, location radius, maps, shop detail pages and sitemap use D1. Stable profile IDs: designworks-{id}.
  4. Preserved the separate intake workflow.
    The form checks duplicates against the directory but still writes to SHOP_INTAKE_DB; seven earlier submissions remain distinct from published shops. No automatic publication.
  5. Built, tested and deployed manually.
    Shop search/map/profile tests passed locally; sitemap had 351 unique shop IDs. Production /shops, /city/seattle, /sitemap.xml and /add-barbershop returned HTTP 200. Owner visually verified live Seattle and Bothell profiles.

Owner decisions

What we decided.

DecisionReason / operating rule
One directory corpusThe 351 Designworks rows are the only approved authoritative directory; no silent merge with the old API’s larger dataset.
Preserve the complete snapshotKeep existing IDs, provenance and statuses. Defer potential duplicates, coordinate gaps and city-name cleanup rather than delaying deployment.
Keep publication separate from intakeExisting submissions stay in a different D1 database and do not become public shops automatically.
Use the existing WorkerRead directory data directly through DIRECTORY_DB instead of introducing another customer API service.
Owner-controlled deploymentBuild with vinext, deploy manually to Cloudflare, and retain Git/Cloudflare release history for rollback.
Do not retire legacy services prematurelyAudit any other consumers of the former directory API before removing it. A working customer site does not prove all other integrations have moved.
